# CHANGELOG 2026-05-27 03:35 — Fix DnD card jump-back via flushSync

Plugin: v1.4.8 → v1.4.9 (patch — bug fix only, no API surface change).

Fixes the long-standing user-reported bug where dragging an approval-set
card from one lane to another in the Approvals pipeline kanban caused
the card to animate to the destination lane and then visually snap back
to the source lane, despite the server correctly persisting the new
status (visible after a manual page reload).

Three prior code-only attempts (`204d507`, `1bc05e8`, `e4604e0`) failed
because they all addressed the cache-write layer without addressing the
real failure mode: a render-timing race between TanStack Query's observer
notification and `@hello-pangea/dnd`'s post-drop IDLE-phase paint. The
prior handover doc (`docs/HANDOVER-DnD-jump-back-bug.md`, committed in
`68d545e`) catalogued the failed attempts and recommended instrumenting
the runtime. Instead of instrumenting first, this fix is a one-shot
applied after a senior-dev read of the full data flow (REST → cache →
hook → useListState → KanbanBoard → @hello-pangea/dnd Droppable) which
isolated the timing race as the single remaining unexplained mechanism.

## Root cause

`@hello-pangea/dnd`'s drop lifecycle:
1. `DROP_ANIMATING` — library renders the dragged card at the destination
   position via an internal transform-override (the smooth animation).
2. Animation completes → `onDragEnd` callback fires.
3. `IDLE` — transform-override is removed; the card is now positioned
   purely from the consumer's `items` prop.

If the consumer's `items` prop has not yet reflected the move when phase
transitions to IDLE, the card paints in its source position → user sees
"jump back". A subsequent React commit fixes the data, but with React
18's automatic batching the visible artifact is the snap-back.

Our flow:
- `onDragEnd` → `handleMove` → `updateStatus` → `setQueriesData`.
- `setQueriesData` is synchronous to the cache, but observer notification
  goes through `useSyncExternalStore`, which **schedules** a render rather
  than committing it inside the current event handler.
- `onDragEnd` returns → `@hello-pangea/dnd` transitions to IDLE → browser
  paints with stale `items` → snap-back.
- React then commits the scheduled render → `items` updated → card moves
  to destination on the next paint.

User perceives this two-frame sequence as a snap-back because frame 1
(stale items, IDLE) and frame 2 (correct items, IDLE) are visually
distinct, and frame 1 places the card in the source lane.

## The fix

`flushSync` from `react-dom` forces a scheduled render to commit
synchronously inside the current call stack, before the wrapping
function returns. Wrapping the optimistic `setQueriesData` call (and
the rollback in the `.catch` branch) in `flushSync` ensures the React
commit happens BEFORE `onDragEnd` returns, so by the time the library
transitions to IDLE the consumer's `items` prop already reflects the
move and the dragged card paints in the destination lane on the very
first IDLE frame.

This is the documented and idiomatic React 18 pattern for integrating
external stores (TanStack Query, Zustand, etc.) with controlled-list
DnD libraries.

## Risk assessment

- **Performance:** `flushSync` forces a synchronous render. For the
  Approvals kanban with typical workloads (5-50 cards), the render is
  measured in single-digit milliseconds — well under one frame. Even
  with 500 cards it would remain under 50ms, which is acceptable for a
  user-initiated event. No measurable user-visible latency.
- **React warnings:** `flushSync` warns when called inside a lifecycle
  (effect, render). Our call sites are inside an event-handler callback
  (`onDragEnd` → `handleMove` → `updateStatus`), which is the documented
  safe context. No warnings expected.
- **Other observers re-render synchronously:** Verified via grep — no
  other component subscribes to the `['approvals', 'listSets', *]` query
  slot beyond the two `useApprovalSets()` consumers in the same render
  subtree. Synchronous re-render of that subtree is desired.
- **If the timing race is NOT the root cause:** Worst case, the fix
  becomes a no-op (no snap-back fix) and 5 lines need to be rolled back.
  We then have definitive evidence that timing is not the bug, which
  unlocks the instrumentation path (Network tab + console-log at
  mutate boundaries + TanStack Query DevTools). Cost: minimal.

## Manual test plan

1. Hard-refresh the Approvals Pipeline page in WP admin
   (`?localwp_auto_login=1`).
2. Ensure at least two approval sets exist, in different statuses
   (e.g. one "Draft", one "Internal").
3. **Primary repro (golden path):** Drag the "Draft" card to the
   "Internal" lane. The card should animate to the destination AND STAY
   THERE. No snap-back. No reload required.
4. Drag the card back from "Internal" to "Draft". Same — should stay.
5. Drag across non-adjacent lanes (e.g. "Draft" → "Live"). Should stay.
6. Drag, then immediately drag again (rapid moves). Both should land.
7. **Verify server-side persistence:** Reload the page. The card should
   be in whichever lane it was last dropped into.
8. **Regression checks (unchanged behavior):**
   - Filter/sort bar still works.
   - "Copy link" action chip still copies to clipboard.
   - "View feedback" action chip still opens the dialog.
   - Preview-on-click still opens the preview dialog.
   - Filter-empty state still shows the "No sets match your filters"
     notice with empty lanes visible.
   - Data-empty state still shows the onboarding empty state.
9. **Negative-path verification (best-effort):** Temporarily break the
   network (DevTools → Network → offline) and try a drag. The card
   should optimistically move, fail server-side, rollback to source
   without visual artifact (one flushSync'd revert frame). A toast
   should surface the error.

If step 3 still shows a snap-back, the timing-race hypothesis was wrong.
Next move per handover doc: instrument with `console.log` at
`updateStatus` boundaries + Network tab + TanStack Query DevTools.
