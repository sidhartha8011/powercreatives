# CHANGELOG 2026-05-27 04:10 — DnD jump-back DIAGNOSTIC build

Plugin: v1.4.9 → v1.4.10 (diagnostic — NOT a fix).

The v1.4.9 flushSync fix did NOT resolve the user-reported snap-back.
That means the render-timing-race hypothesis was wrong. Per
[[feedback_debug_runtime_bugs_data_first]] in auto-memory: stop
theorizing and instrument.

This build adds `console.log` at every boundary in the DnD → cache →
re-render chain. NO fix attempted. The build's only purpose is to
produce diagnostic output the next session can act on.

## What was added

### `app/src/modules/Approvals/hooks/useApprovalSets.ts → updateStatus`

- `console.group('[approvals-dnd] updateStatus id=… → …')` with:
  - All `queryKey`s currently in the React Query cache (to verify the
    prefix `['approvals', 'listSets']` actually matches a slot).
  - `getQueriesData` result (slot count + snapshots).
  - The card's status BEFORE the optimistic write.
- After the `flushSync(setQueriesData)`: log the card's status read back
  from the cache. If this prints the OLD status, the write didn't land.
  If it prints the NEW status, the cache is fine and the bug is
  downstream (in the render → DnD lifecycle).
- `.then()` log on mutation resolve, with the response payload and the
  cache state at resolve time (so we see if the cache somehow gets
  reverted between the optimistic write and server resolve).
- `.catch()` log on mutation reject, with the error (so we know if a
  silent failure is triggering rollback).

### `app/src/modules/Approvals/kanban/SetsBoard.tsx`

- `handleMove`: logs the incoming `KanbanMoveEvent` and explicitly
  warns if it bails due to `isApprovalStatus` or `Number.isFinite`
  guards (those would prevent `updateStatus` from being called at all
  — the absolute first thing to rule out).
- Render-trace at the top of `SetsBoard`: logs every render with
  `sets.length`, `filteredItems.length`, and the first three cards'
  `id:status` pairs. This tells us whether the optimistic write
  actually triggers a re-render that flows through to KanbanBoard,
  and what items KanbanBoard receives.

## How to use this build

1. `cd app && npm run build` (or `npm run build:watch` if not already
   running).
2. Hard-refresh the Approvals Pipeline page in WP admin.
3. Open browser DevTools → Console tab. Filter on `approvals-dnd`.
4. Open DevTools → Network tab. Filter on `status`.
5. Drag a card from one lane to another.
6. Observe the snap-back (or its absence).
7. Copy the entire `[approvals-dnd]` console output back to the next
   session.
8. From Network tab, copy:
   - Request URL.
   - Status code.
   - Request method + body (Headers + Payload tabs).
   - Response body (Response tab).
9. Paste both into the chat.

The next session will be able to identify the root cause within
minutes of seeing the actual runtime data — there are only a handful
of failure modes consistent with the log shape, and each one points to
a specific 5-10 line fix.

## To remove this instrumentation

Once root cause is identified and fixed:

```
grep -rn 'approvals-dnd' app/src/
```

…and delete every matching line. They're all single-line
`console.log/warn/error` calls (or the small `console.group/groupEnd`
pair) so removal is mechanical, no logic untangling needed.
