# CHANGELOG 2026-05-27 04:25 — DnD jump-back ROOT FIX (string/number ID coercion)

Plugin: v1.4.10 → v1.4.11 (patch — actual root-cause fix).

## Root cause (finally, with data)

The 2026-05-27 04:10 diagnostic build (v1.4.10) produced this in the
browser console when the user dragged set id=6 from Draft to Internal:

```
[approvals-dnd] updateStatus id=6 → internal  (t=13807.0ms)
matched slots via prefix: 1 snapshots: [Array(2)]
card BEFORE optimistic write: undefined
[approvals-dnd] AFTER flushSync cache state — card status: undefined (expected internal)
[approvals-dnd] mutateAsync RESOLVED for id=6   {id: '6', userId: '1', brandId: '11', ...}
[approvals-dnd] cache state at resolve — card status: undefined (expected still internal)
```

**Key signal:** the cache slot WAS found (`matched slots: 1`), but
`find(s => s.id === id)` returned `undefined`, both before and after the
optimistic write. The mutation's RESOLVED payload reveals why:

`{id: '6', userId: '1', brandId: '11', ...}` — `id` is a **string**,
not a number.

WordPress / MySQL serializes `BIGINT` columns as JSON strings (a
long-standing quirk of `wp_send_json` + `wpdb::get_results` returning
all column values as PHP strings). The TypeScript type declares
`ApprovalSet.id: number`, but the runtime value is `string`. Every
strict-equality comparison `s.id === id` between the cache's `'6'` and
our `Number(event.itemId)` of `6` returns false.

Concrete consequence in `updateStatus`:

```ts
return prev.map((s) => (s.id === id ? { ...s, status: next } : s));
//                       '6' === 6   →   false   for EVERY card
```

The map produces a structurally-new array with no card changed.
`setQueriesData` writes that no-op array to the cache. The observer is
notified, React re-renders, but the items prop on KanbanBoard is
effectively unchanged — the dragged card is still in its source column
in the data. `@hello-pangea/dnd` finishes its drop animation, removes
its visual transform override, and the card paints in the source lane
because that is where the (unchanged) data places it. **Snap-back.**

## Why all four prior fix attempts failed

Every prior commit (`204d507`, `1bc05e8`, `e4604e0`, `a4ed953`) was a
different theory about the cache-write mechanism — invalidation timing,
microtask ordering, prefix vs exact key matching, render commit timing
via flushSync. Each was a valid hypothesis on its own, but all
operated downstream of the predicate that was never matching anything
in the first place. The optimistic update was a no-op in every
attempt; the cache write produced a fresh array reference but never
changed a single card's status. Without instrumentation, the false
premise was invisible.

## The fix

Two coordinated changes in `useApprovalSets.ts`:

### 1. Boundary normalization in the `sets` memo (TS-type honesty)

```ts
return (query.data as ApprovalSet[]).map((raw) => ({
  ...raw,
  id: Number(raw.id),
  userId: Number(raw.userId),
  brandId: raw.brandId != null ? Number(raw.brandId) : null,
  projectId: raw.projectId != null ? Number(raw.projectId) : null,
}));
```

Coerces server-returned BIGINT strings to numbers at the single point
where the data enters React land. This makes the declared TS type
(`id: number`) actually true for every downstream consumer.

### 2. `Number()` coercion in the cache-write predicate and diagnostic finds

The cache holds the RAW server response, not the normalized `sets` (a
React Query design choice — derived state lives outside the cache).
So inside `updateStatus`, the predicate that reads from cache must
coerce explicitly:

```ts
queryClient.setQueriesData<ApprovalSet[]>(filter, (prev) => {
  if (!prev) return prev;
  return prev.map((s) =>
    Number(s.id) === id ? { ...s, status: next } : s
  );
});
```

`Number(s.id)` returns the same number if `s.id` is already a number,
so the predicate is forward-compatible if/when the server is fixed to
return real integers.

The diagnostic `find` ops (`beforeCard`, `afterCard`, `postCard`) are
updated identically so the next log output is meaningful.

## What is NOT fixed (deferred, separate scope)

These are visible in the same codebase but out of scope for this bug:

- `userId`, `brandId`, `projectId` are also strings in the server
  response. Normalized here for ApprovalSet, but the same pattern
  almost certainly exists for the other Approval-side types
  (Project, Brand snapshots in `set.snapshot`). Snapshot fields are
  not currently used in strict-equality comparisons, so latent. Worth
  a separate sweep.
- The PHP service should be fixed to return integers for numeric
  columns (`format_set_row()` could cast via `(int)`). That's the
  cleaner long-term fix — the client coercion would then be defensive
  but redundant. Separate task.
- The duplicate `useApprovalSets()` call in `index.tsx` (called
  alongside `SetsBoard.tsx`). Code smell, no UX impact. Separate task.
- The `void updateStatus(...)` fire-and-forget. Errors only surface
  via toast. Separate task.
