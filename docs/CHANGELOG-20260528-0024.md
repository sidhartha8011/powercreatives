# CHANGELOG 2026-05-28 00:24 — Deliveries module (Task 1 of 2)

Plugin: v1.5.0 → v1.6.0 (minor — new feature module).
DB:     v1.9.0 → v1.10.0 (new table: `pcm_deliveries`).

## Why

Per [docs/HANDOVER-Approvals-per-asset-tagging.md](HANDOVER-Approvals-per-asset-tagging.md):
Approvals' per-asset brand/project/delivery tagging (Task 2) needs a
real Deliveries module to reference. Task 1 builds that module standalone
— no Approvals coupling yet. Mirrors the Brands module pattern so adding
new modules to the platform keeps feeling familiar.

## What ships

A fully functional Deliveries module with a Kanban pipeline UI. The
previous 116-line stub (no backend, no handlers) is fully replaced.

### Behaviour

- **Kanban pipeline**, 3 columns: Active / Paused / Completed.
- **Drag-and-drop** between columns issues a status change with the
  flushSync optimistic-update pattern (no card snap-back, same as
  Approvals — see CHANGELOG-20260527-0425.md for the autopsy).
- **Filter bar** with search (name + clientName) + client dropdown +
  sort dropdown. Mirrors the Approvals SetsBoard bar pixel-for-pixel.
- **Empty states** split into two: truly-empty data shows an onboarding
  CTA; filter-empty keeps the board visible and surfaces a Clear-filters
  notice above it. Matches Approvals.
- **Create / Edit / Delete** via shadcn `Dialog` (create + edit share one
  dialog, two modes) and `AlertDialog` (delete confirmation).
- **Ownership-scoped** at every layer — REST controller, service,
  PCM_DB. A user can never see or mutate another user's delivery.

## Backend

### Schema

`includes/core/db/class-pcm-schema.php`
- New `dbDelta` block for `pcm_deliveries` placed in the canonical
  position (right before `pcm_approval_sets`). Columns:
  `id, userId, name, clientName, status, createdAt, updatedAt`.
  Indexes: `userId`, `status`.
- `drop_tables()` list gains `'deliveries'` so plugin-data-deletion
  cleans up the table.

`power-creatives.php`
- `PCM_VERSION` 1.5.0 → 1.6.0 (also in the plugin header `Version:`).
- `PCM_DB_VERSION` 1.9.0 → 1.10.0. `PCM_Activator::maybe_upgrade()`
  re-runs `create_tables()` (idempotent `dbDelta`) on the next request,
  picking up the new table without an explicit migration block.

### Data layer

`includes/core/db/class-pcm-db.php`
- New `// DELIVERIES` section with five static methods mirroring the
  Brands shape:
  - `get_user_deliveries(int $user_id): array` — cached list, 5min TTL.
  - `get_delivery_by_id(int $id, int $user_id): ?object` — direct read,
    ownership-scoped.
  - `create_delivery(array $data): int|false` — insert + cache invalidate.
  - `update_delivery(int $id, int $user_id, array $data): bool` —
    auto-stamps `updatedAt`, ownership-scoped, cache invalidate.
  - `delete_delivery(int $id, int $user_id): bool` — ownership-scoped,
    cache invalidate.

### Module (auto-discovered via `includes/module-loader.php`)

`includes/modules/deliveries/config.php`
- Module metadata for the discovery scan (`PCM_REST_Deliveries`,
  namespace `pcm/v1/deliveries`).

`includes/modules/deliveries/service.php`
- `PCM_Deliveries_Service::STATUSES = ['active', 'paused', 'completed']`
  — source of truth for both server-side validation and the Kanban
  column declaration. Mirrored on the frontend in `types.ts`.
- `format_delivery(object $row): array` — coerces numeric BIGINT
  columns to PHP `int` so the JSON payload contains numbers, not
  strings. The frontend hook still defensively re-normalizes via
  `Number()`, but this keeps the wire format honest.
- `validate_status(mixed $status): ?string` — returns the status if in
  the allowed set, null otherwise. Used by the controller to reject bad
  input with a 400 before touching the DB.

`includes/modules/deliveries/controller.php`
- `PCM_REST_Deliveries extends PCM_REST_Base` — five routes:
  `GET /deliveries`, `GET /deliveries/<id>`, `POST /deliveries`,
  `PATCH /deliveries/<id>`, `DELETE /deliveries/<id>`.
- Default permission (manage_options) — gate-auth visitors are admitted
  by `PCM_REST_Base::make_permission_callback` exactly like Brands.
- Create + Update validate `status` and `name` up-front, returning the
  freshly-read row so the frontend can update its cache without a second
  fetch.

## Frontend

### tRPC

`app/src/lib/trpc.ts`
- New `// ── Deliveries ──` block (right after Brands): `deliveries.list`,
  `deliveries.getById`, `deliveries.create`, `deliveries.update`,
  `deliveries.delete`. Transforms match the Brands shape.

### Types

`app/src/modules/Deliveries/types.ts`
- `DELIVERY_STATUSES = ['active', 'paused', 'completed'] as const`.
- `DeliveryStatus` union derived from the const array.
- `Delivery` interface — single source of truth for the row shape.

### Hook

`app/src/modules/Deliveries/hooks/useDeliveries.ts`
- `useDeliveries()` — list query + 4 mutations (create / update /
  status-change / delete). Status mutation wraps the optimistic
  setQueriesData write in `flushSync()` so @hello-pangea/dnd's IDLE
  paint sees the new column before snapping the card back. Same proven
  pattern as `useApprovalSets.updateStatus`.
- **Boundary normalization**: every list-derived item runs through a
  `useMemo` that coerces `id` + `userId` via `Number()`. This neutralizes
  the WP/MySQL BIGINT-as-string bug from the v1.4.x DnD jump-back
  incident — predicates like `Number(d.id) === id` always match
  regardless of whether the cache holds strings or numbers.
- **Dialog state intentionally NOT inside the hook.** Multiple consumers
  call this hook (board + module entry); state inside the hook would be
  per-instance and desync. Dialog state lives in the module entry, see
  `index.tsx`.

### Kanban consumer (uses the shared primitive)

`app/src/modules/Deliveries/kanban/deliveryColumns.ts`
- 3 columns matching `DELIVERY_STATUSES`. Color palette borrows from
  Approvals' tokens so the two pipelines feel like siblings.

`app/src/modules/Deliveries/kanban/deliveryFilters.ts`
- Text filter (search across name + clientName) + searchable client
  dropdown. One declaration per filter — extend by appending one line.

`app/src/modules/Deliveries/kanban/deliverySorts.ts`
- Four sorts: Recently updated (default), Newest first, Oldest first,
  Name A→Z.

`app/src/modules/Deliveries/kanban/DeliveryCard.tsx`
- Card body: name + clientName + relative-updatedAt + hover-revealed
  Edit / Delete dropdown. Click body = open edit. Drag = move column.
  Notion-style; keyboard-accessible (Enter / Space).

`app/src/modules/Deliveries/kanban/DeliveriesBoard.tsx`
- Mirrors `Approvals/kanban/SetsBoard.tsx`. Owns the filter bar, the
  delete-confirm AlertDialog, the truly-empty vs filter-empty split,
  and the `onItemMove` → `updateStatus` wiring.

### Module entry + dialog

`app/src/modules/Deliveries/DeliveryDialog.tsx`
- Single dialog handles both create and edit. Form auto-syncs to the
  supplied delivery on `open` transitions. Submit disabled while the
  mutation is pending so users cannot double-submit.

`app/src/modules/Deliveries/index.tsx`
- Module entry. Hosts the `ModuleHeader` + primary "New Delivery"
  action, mounts the `DeliveriesBoard` and the `DeliveryDialog`, and
  owns dialog state (lifted out of the hook for the reason noted above).
- Old 116-line stub fully replaced — `useState<Delivery[]>([])`,
  unhandled "+ New Delivery" button, and the inline card-grid markup
  are all gone.

## Out of scope (intentional, deferred to Task 2 or later)

- **Per-asset tagging in Approvals.** That's Task 2. This module is
  standalone — Approvals does not yet reference `deliveryId`.
- **Project linkage / `projectCount` on cards.** Will arrive when
  projects start referencing deliveries (Task 2 territory). For now the
  card shows `name + clientName + updatedAt` and that's the right
  amount.
- **Bulk operations.** Brands has bulk delete + duplicate; Deliveries
  doesn't yet need them. Add when usage data shows the gap.
- **Asset handling, color extraction, URL scraping.** These are
  Brands-specific concerns, not relevant for Deliveries.
